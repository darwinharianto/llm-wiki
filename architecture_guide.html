Andrej Karpathy's Compiled Knowledge Pattern

How LLM Wiki Ingests, Consolidates, Stores, and Displays Knowledge

Unlike stateless vector RAG—which slices raw documents into isolated chunks, stores duplicate copies forever, and re-synthesizes from scratch at query time—LLM Wiki compiles incoming documents into a self-maintaining, interlinked Markdown vault on disk. Every new source is compared against existing pages first: redundant passages are deduplicated, while novel facts and contradictions update the canonical page in-place with a full unified diff audit trail.

Traditional Stateless Vector RAG (E5-Large) ~80% Top-10 Wasted Slots at 10x

Raw Docs (10x Redundant) → Fixed Chunking → Dense Embedding Index → Top-K Retrieval Polluted by 10 Identical Copies

  • No write-time deduplication: 10 waves of 536 passages create 5,360 separate vector entries.
  • Top-10 results collapse to just 2.01 unique topics (79.9% duplicate slots).
  • Counterfactual updates sit alongside outdated chunks with no explicit contradiction record.
Compiled LLM Wiki (Write-Time Synthesis) 99.67% Redundancy Consolidated

Raw Doc → vault/raw/ → 4-Signal Similarity Check → In-Place Page Update + Unified Diff → Interlinked Markdown Vault

  • Consolidates 5,360 English passages into 548 pages (and 2,035 Japanese passages into 407 pages).
  • Preserves 9.56 / 10 unique topics in Top-10 (`R@10 = 95.85%` vs E5's `64.24%`).
  • Tracks every revision in vault/.history/ and surfaces tensions under ## Contradictions & Tensions.

3. Deep-Dive: How LLM Wiki Ingests, Deduplicates & Synthesizes Data

Click any stage below to inspect the exact algorithms, mathematical formulas, and code paths executed during ingestion.

Stage 1 — Immutable Raw Archival & Candidate Topic Extraction (WikiEngine.preview_ingest / LLMService.extract_candidates)

When you submit a document via the UI or POST /api/ingest/execute, LLM Wiki never discards your original text:

  1. Archive Raw Source: VaultManager.save_raw_source(title, content, source_name) writes an immutable copy to vault/raw/<UTC-timestamp>-<slug>.md with YAML metadata (title, ingested_at).
  2. Extract Candidate Topic(s):
    • In Cloud/Local LLM mode (gemini / openai / ollama), the LLM extracts structured JSON candidates (title, category, aliases, tags, summary, body).
    • In Smart Offline Synthesis mode (local_smart), _local_extract_candidates() infers the category (concepts, entities, comparisons, sources, syntheses), extracts top domain tags via _extract_tags(), and weaves outbound [[slug|Title]] wikilinks for any existing wiki entities mentioned in the prose via _weave_wikilinks().
Stage 2 — Multilingual (English + Japanese/CJK) Tokenization & Inverted Index (backend/similarity.py)

To run 100% locally in milliseconds without external vector DB dependencies, HybridSimilarityEngine builds an in-memory inverted index over all pages in vault/wiki/:

English / Technical 3GPP Fast Path

When has_cjk(text) is False, tokenize() extracts [a-z0-9]+ tokens (len > 1) and removes STOPWORDS, preserving technical identifiers like ts, 38, 401, ran2, pdcp, and gnodeb.

Japanese / CJK NFKC Morpheme & N-Gram Path

When has_cjk(text) is True, tokenize() applies unicodedata.normalize("NFKC", text) and extracts:

  • Kanji runs ([\u4e00-\u9fff...]+) + overlapping 2-char Kanji bigrams for compound nouns (東大寺の仏像 → 東大寺, 東大, 大寺, 仏像)
  • Katakana runs ([\u30a0-\u30ffー]+) + 2–3 char sub-grams for loanwords
  • Hiragana stems with trailing particle stripping and JA_STOPWORDS filtering
Stage 3 — 4-Signal Hybrid Similarity Routing: UPDATE vs. CREATE (find_similar_for_candidate)

Before creating any file, HybridSimilarityEngine.find_similar_for_candidate() retrieves the top candidate pages from its Title, BM25, and TF-IDF postings lists and computes a weighted composite score: 

Composite Score = 0.32 × Title_Alias_Score
                + 0.30 × Okapi_BM25_Score (k1 = 1.5, b = 0.75)
                + 0.23 × TFIDF_Cosine_Score (unigrams + word bigrams + title char trigrams)
                + 0.15 × Graph_Tag_Link_Jaccard
When does it route to UPDATE (score >= 0.35)?

1. Title/Alias Inclusion (has_title_inclusion): Exact slug match, alias match, or multi-token title substring match.
2. Blind-Title Near-Duplicate Body (is_near_dup_body): Even if the incoming document has a completely different, blind title (e.g., 3GPP Archive Memo #08-042 or 調査メモ #012), if tf_sc >= 0.84 or (tf_sc >= 0.52 and body_containment >= 0.92 and body_jaccard >= 0.88) against the clean prose body (body_tok_sets[slug]), it routes to UPDATE!

How does it prevent false merges between sibling clauses?

In technical specs (like 3GPP TeleQuAD or Wikipedia articles with multiple sections), two distinct passages may share domain vocabulary. If a full passage (>= 12 body tokens) has neither title inclusion nor a near-duplicate body, its score is capped at 0.34 × tf_sc (below the 0.35 threshold) so distinct sub-clauses create separate canonical pages.

Stage 4 — Sentence-Level Redundancy Filtering vs. Counterfactual Update Synthesis (_local_synthesize_page_update)

Once an incoming document is routed to UPDATE an existing page, LLM Wiki does not blindly append the whole document. Instead, _local_synthesize_page_update() splits the incoming text into paragraphs and technical sentences (via _split_technical_sentences(), which respects e.g., i.e., Fig., Dr., and Japanese 。！？) and checks each unit with _is_redundant_unit():

  • Novel Number / Counterfactual Guard (Checked First!): _extract_numbers() extracts all numeric values (including numbers attached to Japanese counters like 1958年 or 341.5メートル). If a sentence introduces any new number not present in the existing page (`unit_nums - existing_numbers`), _is_redundant_unit() immediately returns False so factual revisions and counterfactual updates are never dropped.
  • Normalized Substring Check: If the normalized sentence is already a substring of the existing page body and introduces no new numbers, it is skipped as redundant.
  • Token Containment Check (`>= 0.78`): If >= 78% of the sentence's tokens already appear in any existing paragraph or sentence segment on the page, it is skipped.
  • Word-Bigram Containment Check (`>= 0.75`): If >= 75% of the sentence's 2-word phrases already exist in the page's bigram set, it is skipped—even if sentences were re-ordered or merged across waves.
  • Contradiction & Tension Detection: Any kept novel block containing a marker in CONTRADICTION_MARKERS (however, contrary to, unlike, supersedes, revision, しかし, 改訂, etc.) is also logged under ## Contradictions & Tensions with a source/date stamp.
Stage 5 — Incremental Index Upsert, Unified Diff Snapshot & Self-Healing Linter (VaultManager & WikiLinter)

After synthesis completes:

  1. VaultManager.save_page() increments revision_count, appends the raw source filename to sources in the YAML frontmatter, writes the unified diff JSON to vault/.history/<slug>/<timestamp>.json, and updates vault/wiki/<category>/<slug>.md.
  2. VaultManager.rebuild_index_md() regenerates vault/index.md and VaultManager.append_log() records the operation in vault/log.md.
  3. If auto_maintain_after_ingest is enabled, WikiLinter.auto_maintain() scans all pages for unlinked entity mentions, orphan pages with 0 inbound/outbound links, and dangling [[wikilinks]], automatically weaving missing links and connecting isolated pages into the knowledge graph.

5. How the Web UI Fetches & Displays the Compiled Knowledge Base

        

          The single-page studio in frontend/index.html + frontend/app.js communicates with FastAPI in backend/app.py through 11 JSON endpoints.
        

      


      

        

          

            1. Wiki Explorer & Diff Drawer
            GET /api/pages/{slug}
          

          

            Loads the compiled page's YAML metadata, rendered Markdown body (converting [[slug|Label]] into clickable internal navigation pills), outbound links, incoming backlinks, raw source badges, and the .history/<slug>/*.json revision timeline with color-coded unified diffs.
          

        


        

          

            2. Force-Directed Graph Canvas
            GET /api/graph
          

          

            Computes every node (sized by degree + revision count, colored by category) and two edge layers: solid explicit [[wikilink]] edges and dashed semantic similarity edges. Rendered interactively on an HTML5 <canvas> with repulsion/spring physics, zoom/pan, and click-to-inspect.
          

        


        

          

            3. Similarity-First Ingest Studio
            POST /api/ingest/preview
          

          

            Before writing a single byte to vault/wiki/, the UI previews each extracted candidate topic with its 4-signal similarity breakdown bar and recommended action (UPDATE [[existing-slug]] vs CREATE new page), plus a manual target override selector.
          

        


        

          

            4. Self-Healing Linter Center
            POST /api/lint/heal
          

          

            Displays the 0–100% Vault Health Score and lists unlinked entity mentions, orphan pages, dangling wikilinks, and near-duplicate page pairs (`>= threshold`), allowing one-click automatic link weaving, stub creation, or explicit page merging (`POST /api/merge`).
          

        


        

          

            5. Grounded Chat & File-to-Wiki
            POST /api/chat
          

          

            Retrieves the top wiki pages via HybridSimilarityEngine.search(), extracts pinpoint technical sentences for the Direct Answer, surfaces any ## Contradictions & Tensions, and lets you click File Answer into Wiki (POST /api/chat/file-to-wiki) so valuable Q&A syntheses compound back into the vault.
          

        


        

          

            6. Live Provider Switcher
            POST /api/settings
          

          

            Switch at runtime between Google Gemini (`gemini-3.5-flash-lite`), OpenAI-compatible endpoints, Ollama local models, and Smart Offline Synthesis (`local_smart`), and tune the similarity threshold (`0.35`) live.
